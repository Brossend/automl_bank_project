# Model Card - прогноз отклика клиента на депозит

Проект - automl_bank_project
Тип задачи - бинарная классификация
Статус - учебный проект. Модель обучается и запускается локально, интеграции с CRM пока нет.

Документ составлен по структуре Google Model Cards.

## 1. Сведения о модели (Model Details)

| Параметр | Значение |
|---|---|
| Название | Bank Marketing Deposit Response Prediction |
| Разработчик | Иван Лямцев |
| Задача | Предсказать, согласится ли клиент открыть срочный депозит после маркетингового звонка |
| Алгоритм | ExtraTreesClassifier (scikit-learn) |
| Подбор модели | Optuna, сравнение с LogisticRegression и RandomForestClassifier |
| Обработка данных | StandardScaler для числовых признаков, OneHotEncoder для категориальных |
| Сохранение модели | models/best_model.joblib (Pipeline вместе с обработкой данных) |
| Запуск прогноза | Функция predict_client() из src/predict.py или командная строка |
| Основная метрика | F1-score |
| Порог классификации | 0.5 |

Модель подбирается в src/train.py через Optuna. По умолчанию выполняется 20 испытаний с random_state=42.

В сохранённом отчёте выбрана следующая конфигурация:

| Параметр | Значение |
|---|---|
| model | extra_trees |
| n_estimators | 94 |
| max_depth | 17 |
| min_samples_split | 7 |
| min_samples_leaf | 1 |
| class_weight | balanced |

Это параметры конкретного запуска. При повторном обучении результат может отличаться.

## 2. Для чего нужна модель (Intended Use)

Модель оценивает, насколько вероятен положительный отклик клиента на предложение депозита. В банке такой прогноз можно использовать для составления очереди обзвона. Сначала связываться с клиентами с более высоким скором, а не обзванивать всех в произвольном порядке.

Предполагаемые пользователи - маркетинговые аналитики и сотрудники контакт-центра. Сейчас модель используется как учебный прототип через Python.

В проекте реализованы загрузка и подготовка данных, обучение, оценка, сохранение модели и локальный прогноз. Подключения к CRM, API и автоматического формирования списков звонков пока нет.

Модель не предназначена для выдачи кредитов, оценки платёжеспособности или автоматического отказа клиентам в банковских услугах. Перед использованием в другом банке или на новых данных её потребуется проверить заново.

## 3. Входные и выходные данные (Input and Output)

На вход подаётся информация о клиенте и истории контактов. Всего используется 15 признаков.

| Признак | Тип | Описание |
|---|---|---|
| age | Числовой | Возраст |
| job | Категориальный | Род занятий |
| marital | Категориальный | Семейное положение |
| education | Категориальный | Образование |
| default | Категориальный | Наличие кредитного дефолта |
| balance | Числовой | Средний годовой баланс счёта |
| housing | Категориальный | Жилищный кредит |
| loan | Категориальный | Персональный кредит |
| contact | Категориальный | Тип связи |
| day | Числовой | День последнего контакта |
| month | Категориальный | Месяц последнего контакта |
| campaign | Числовой | Количество контактов в текущей кампании |
| pdays | Числовой | Дней после контакта в предыдущей кампании (-1, если его не было) |
| previous | Числовой | Количество контактов в предыдущих кампаниях |
| poutcome | Категориальный | Результат предыдущей кампании |

Поле y - правильный ответ для обучения (yes = 1, no = 0). Для прогноза новому клиенту оно не требуется.

Поле duration исключено. Это длительность текущего звонка, которую нельзя знать до контакта с клиентом. Если оставить её при обучении, модель будет опираться на данные, недоступные в момент прогноза.

Функция predict_client() принимает JSON с признаками и возвращает два значения.

```json
{
  "prediction": 1,
  "probability_yes": 0.73
}
```

Это пример формата ответа, а не результат предсказания для конкретного клиента.

- prediction - класс 0 или 1 по порогу 0.5
- probability_yes - скор положительного класса от 0 до 1

Для неизвестных категорий используется OneHotEncoder с handle_unknown="ignore". Это позволяет обработать новые значения, но не гарантирует точность прогноза. Калибровка вероятностей отдельно не проводилась, поэтому скор не стоит воспринимать как точную вероятность открытия депозита.

## 4. Факторы, влияющие на результат (Factors)

Модель учитывает сведения о клиенте, его финансах, канале связи и предыдущих контактах. В том числе результат может зависеть от месяца и количества звонков.

Важно, что модель обучалась на исторических данных. Она может перенимать особенности старых маркетинговых кампаний. Качество прогнозов для разных возрастов, профессий и каналов связи отдельно не сравнивалось.

## 5. Метрики качества (Metrics)

| Метрика | Что показывает |
|---|---|
| F1-score | Баланс между precision и recall. Используется для выбора модели в Optuna |
| Precision | Какая доля клиентов с прогнозом 1 действительно открыла депозит |
| Recall | Какую долю клиентов, открывших депозит, модель смогла найти |
| ROC-AUC | Насколько хорошо модель разделяет положительный и отрицательный классы при разных порогах |
| Accuracy | Общая доля правильных прогнозов |
| Confusion Matrix | Сколько было верных и ошибочных прогнозов каждого класса |

Основная метрика - F1-score, потому что положительных откликов меньше, чем отказов. Одной accuracy здесь недостаточно.

## 6. Данные для обучения (Training Data)

Источник - [UCI Bank Marketing](https://archive.ics.uci.edu/dataset/222/bank+marketing), исторические данные телефонных кампаний португальского банка. В проекте используется файл bank.csv на 4 521 исходную запись.

В src/etl.py данные очищаются, удаляются дубликаты, обрабатываются пропуски, целевой признак переводится в 0/1, а duration исключается. Числовые и категориальные признаки обрабатываются внутри Pipeline.

Разделение стратифицированное, примерно 60% на обучение, 20% на валидацию и 20% на тест. Используется random_state=42. Разделение случайное, не по времени.

## 7. Как проверялось качество (Evaluation Data)

Сначала Optuna подбирает модель и параметры по F1 на валидации. Затем выбранный Pipeline обучается на объединённых train и validation и проверяется на отдельной тестовой части.

Тестовые данные взяты из того же bank.csv. Поэтому результаты показывают качество на отложенной части исходного набора, а не на клиентах другого банка или будущей кампании. Внешняя проверка и тестирование на новых данных пока не проводились.

## 8. Результаты (Quantitative Analyses)

Метрики из [reports/metrics.json](reports/metrics.json).

| Метрика | Значение | Выборка |
|---|---:|---|
| Лучшая F1 в Optuna | 0.4444 | Валидация |
| Accuracy | 0.8287 | Тест |
| Precision | 0.3023 | Тест |
| Recall | 0.3750 | Тест |
| F1-score | 0.3348 | Тест |
| ROC-AUC | 0.7154 | Тест |

ROC-AUC около 0.72 показывает, что модель различает классы лучше случайного выбора. При этом precision около 0.30 и recall 0.375 остаются невысокими. Часть клиентов получит ошибочно положительный прогноз, а часть заинтересованных клиентов модель пропустит.

Accuracy выглядит выше остальных метрик из-за преобладания отрицательного класса. Для реального обзвона качество нужно дополнительно оценивать по стоимости звонков и результатам кампаний.

Графики и отчёты находятся в reports/figures, результаты подбора параметров - в reports/tables.

## 9. Риски и этические вопросы (Ethical Considerations)

В реальном банке модель работала бы с персональными и финансовыми данными. Для их использования нужны законные основания, защита информации и соблюдение правил контакта с клиентами.

Есть риск, что модель будет хуже работать для отдельных групп клиентов. Возраст, семейное положение, профессия и образование могут влиять на прогноз, но отдельного анализа по группам в проекте нет.

Прогноз не должен самостоятельно решать, кому доступны банковские услуги. Это вспомогательный инструмент для сотрудников, и ошибки модели нужно учитывать.

## 10. Ограничения и дальнейшая работа (Caveats and Recommendations)

- Выборка небольшая и историческая. Для современных клиентов результаты могут отличаться.
- Модель не проверялась на новых кампаниях и данных других банков.
- Вероятности не калиброваны, порог 0.5 не подбирался под экономику обзвона.
- Нет интеграции с CRM, мониторинга качества и автоматического переобучения.
- Перед внедрением нужно проверить модель на актуальных данных, сравнить с простым базовым решением, оценить качество по группам и подобрать рабочий порог.

poetry install
