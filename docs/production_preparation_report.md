# Отчёт о подготовке ML-проекта к production-подходу

## Общая информация

Проект `automl_bank_project` решает задачу бинарной классификации на датасете
Bank Marketing. Модель прогнозирует, согласится ли клиент на срочный депозит.

В рамках учебного задания проект был доработан в три этапа:

1. рефакторинг ML-кода под production-подход;
2. настройка Poetry, Ruff, mypy и pre-commit;
3. интеграция локального виртуального окружения с Git-репозиторием.

Цель работы состояла не в полной переработке проекта, а в устранении проблем
учебного кода и настройке воспроизводимой разработки. ML-алгоритмы, датасет,
целевая переменная и набор метрик при этом не менялись.

## 1. Рефакторинг ML-проекта

### Результаты аудита

Перед изменениями были изучены структура проекта, ETL, обучение, предсказание,
оценка модели, конфигурация, тесты, Docker, GitHub Actions и GitLab CI.

Основные найденные проблемы:

- часть путей к артефактам задавалась непосредственно в рабочих модулях;
- обучение одновременно отвечало за подбор модели, расчёт метрик, построение
  графиков, сохранение модели и работу с MLflow;
- служебные сообщения выводились через `print`;
- публичным функциям не хватало аннотаций типов;
- загрузка данных и предсказание слабо проверяли входные данные;
- Optuna использовал sampler без фиксированного seed;
- сохранение и загрузка модели выполнялись в разных местах;
- не было тестов для ошибок загрузки данных и входных данных предсказания.

### Выполненные изменения

Пути к данным, модели и отчётам собраны в `src/config.py`. Для работы с файловой
системой используется `pathlib.Path`.

Ответственности разделены между небольшими модулями:

- `src/train.py` отвечает за обучение и подбор гиперпараметров;
- `src/predict.py` отвечает за подготовку входных данных и предсказание;
- `src/model_io.py` сохраняет и загружает модель;
- `src/reporting.py` рассчитывает метрики и строит графики;
- `src/logging_utils.py` содержит общую настройку стандартного `logging`.

В ETL добавлены проверки существования и содержимого файла, пустого DataFrame,
целевой переменной и корректности разбиения. Обработка строк работает с типами
данных pandas 2 и pandas 3.

Перед предсказанием проверяются JSON-объект, наличие обязательных признаков,
порог классификации и совместимость значений с моделью. Ошибки отсутствующей или
повреждённой модели теперь сообщаются явно.

Воспроизводимость обеспечивается фиксированным `random_state` для разбиений и
моделей, а также `TPESampler(seed=RANDOM_STATE)` для Optuna. Обучение и
предсказание остаются отдельными процессами. Итоговый preprocessing и модель
по-прежнему сохраняются одним объектом `Pipeline` через joblib.

Тесты дополнены проверками отсутствующего файла данных, воспроизводимого
разбиения, нормализации входа предсказания и отсутствующих признаков. Итоговый
набор содержит 11 тестов.

### Что не менялось

Без необходимости не изменялись:

- датасет Bank Marketing и целевая переменная `y`;
- исключение признака `duration`;
- Logistic Regression, Random Forest и Extra Trees;
- пространство поиска Optuna и целевая метрика F1;
- итоговые метрики Accuracy, Precision, Recall, F1 и ROC-AUC;
- MLflow, Docker и общий порядок работы CI;
- формат сохранённой модели.

## 2. Poetry и проверки кода

Зависимости разработки перенесены в `pyproject.toml` и зафиксированы в
`poetry.lock`. Проект устанавливается как пакет с существующим именем `src` и
поддерживает Python 3.11-3.14.

Основные зависимости отделены от инструментов разработки. `requirements.txt`
сохранён для Dockerfile, а GitHub Actions и GitLab CI используют
`poetry install`.

В проект добавлены следующие инструменты:

- Poetry управляет зависимостями и установкой проекта;
- Ruff проверяет код, сортирует импорты и форматирует Python-файлы;
- mypy проверяет аннотации типов в `src`;
- pytest запускает тесты;
- pre-commit выполняет быстрые проверки перед коммитом.

Конфигурация pre-commit удаляет trailing whitespace, проверяет EOF и YAML,
защищает от случайного добавления больших файлов, запускает Ruff lint и Ruff
format. mypy оставлен отдельной Poetry-командой, так как отдельной проверке
pre-commit потребовалась бы повторная установка тяжёлых ML-зависимостей.

Основные команды проверки:

```bash
poetry install
poetry run ruff check .
poetry run ruff format --check .
poetry run mypy src
poetry run pytest
poetry run pre-commit run --all-files
```

На момент завершения работы все команды выполнялись успешно:

- Ruff lint прошёл без ошибок;
- Ruff подтвердил форматирование 17 Python-файлов;
- mypy не нашёл ошибок в 11 файлах `src`;
- pytest выполнил 11 тестов;
- все 6 pre-commit hooks прошли.

## 3. Виртуальное окружение

Poetry настроен на создание окружения внутри проекта. Локальная настройка
хранится в `poetry.toml`:

```toml
[virtualenvs]
in-project = true
```

Физический путь окружения в проверенном рабочем проекте:

```text
C:\Users\bross\PycharmProjects\automl_bank_project\.venv
```

Каталог `.venv/` указан в `.gitignore`. Команда `git check-ignore -v .venv`
подтвердила, что окружение не попадает в Git.

После клонирования репозитория окружение создаётся командами:

```bash
poetry config virtualenvs.in-project true --local
poetry install
```

Путь, версию Python и состояние окружения можно проверить командой:

```bash
poetry env info
```

Проверенное окружение использовало CPython 3.14.0 и имело состояние
`Valid: True`. Повторный запуск `poetry install` установил проект из lock-файла
без ошибок.

## Итог

Проект был приближен к production-подходу в рамках учебного задания. Код стал
лучше разделён по ответственности, обучение стало воспроизводимым, а ошибки
входных данных обрабатываются понятнее. Poetry и lock-файл обеспечивают
повторяемую установку зависимостей. Ruff, mypy, pytest и pre-commit формируют
единый набор проверок для локальной разработки и CI.

Остаётся известное ограничение. Существующий файл модели был создан в
scikit-learn 1.8, а текущий lock-файл фиксирует scikit-learn 1.9.1. До следующего
переобучения sklearn может выводить предупреждение о различии версий при загрузке
старого артефакта.
